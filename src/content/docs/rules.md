新增或修改這個知識庫的任何內容前，先把這一頁讀完。它是內容層的權威文件。

## 這個知識庫是什麼

這裡整理的是「使用者該學什麼」。來源是使用者 GitHub 上的作品：分析每個存放庫實際用了哪些技術、寫法與目前主流有什麼落差，再把值得學的東西寫成一篇篇條目。

每個條目都要能回答兩個問題：這跟使用者的哪個作品有關？下一步該做什麼？答不出來的內容不屬於這裡，這裡不是通用教科書。

網站是公開的，任何人都看得到。寫入內容時以公開為前提。

## 結構

知識庫根目錄是 `src/content/docs/`，固定三層，不再往下巢狀：

```
src/content/docs/
├── index.md              根索引
├── rules.md              本頁
├── repos/                作品分析，一個存放庫一頁
│   ├── index.md          作品索引
│   └── <repo-name>.md
└── <concept>/            技術概念目錄
    ├── index.md          目錄索引
    └── <topic>.md        知識條目
```

技術概念目錄沒有預先定義，隨分析結果逐步建立。單一目錄超過約 15 篇時，向使用者提議拆分。

## 怎麼找內容

沿索引往下讀，不要掃過所有檔案：

1. 本頁
2. 根索引 `index.md`：有哪些技術概念目錄
3. 相關目錄的 `index.md`：該目錄有哪些條目、各自一句話摘要
4. 只開需要的條目

要找某個存放庫引出了哪些條目，從 `repos/index.md` 進到該存放庫的頁面。

## 頁面種類與欄位

每個 Markdown 檔開頭的 frontmatter 是它的資料欄位。`kind` 決定頁面種類：

| `kind` | 用途 | 必填欄位 |
|---|---|---|
| `entry`（預設，可省略不寫） | 知識條目 | `title`、`description`、`status`、`priority`、`repos`、`updated` |
| `index` | 根索引、目錄索引、作品索引 | `title`、`description` |
| `repo` | 作品分析頁 | `title`、`description` |
| `page` | 其他說明頁，例如本頁 | `title`、`description` |

條目的欄位：

| 欄位 | 填法 |
|---|---|
| `title` | 條目標題，用概念本身的名稱，不加「學習」「筆記」這類字 |
| `description` | 一句話摘要，要與目錄索引中那一列的摘要完全相同 |
| `status` | `todo`（待學習）、`learning`（學習中）、`done`（已掌握）。新條目一律 `todo` |
| `priority` | `high`、`medium`、`low`。依「對使用者作品的影響」判斷，不是依技術本身熱不熱門 |
| `repos` | 引出這個條目的存放庫名稱清單，名稱要與 `repos/` 內的檔名一致 |
| `tags` | 跨目錄的關鍵字，英文小寫。可省略。純數字的標籤要加引號，例如 `"8051"`，否則會被當成數字而驗證失敗 |
| `updated` | 最後一次實質更新的日期，格式 `YYYY-MM-DD`，**不要加引號** |

條目缺少必填欄位，或 `status`、`priority` 填了清單以外的值，建置會失敗。欄位的程式定義在 `src/content.config.ts`。

## 範本

### 知識條目

檔案位置 `src/content/docs/<concept>/<topic>.md`。六個段落的標題與順序固定，不要增減。

```md
---
title: <概念名稱>
description: <一句話摘要>
status: todo
priority: medium
repos:
  - <repo-name>
tags:
  - <keyword>
updated: 2026-01-31
---

## 這是什麼

幾句話講清楚這個概念，以及它解決什麼問題。

## 我的現況

在哪個作品、哪個檔案、目前怎麼做。附檔案路徑，需要時附一小段程式碼。

## 與主流的落差

現在主流怎麼做、差在哪裡、為什麼值得跟上。說法要有來源依據。

## 學習路線

由淺入深的步驟，用編號清單。

## 動手練習

可以直接在自己哪個作品上改什麼，具體到檔案或功能。

## 參考資源

官方文件優先，每項附連結。
```

### 作品分析頁

檔案位置 `src/content/docs/repos/<repo-name>.md`，檔名與 GitHub 上的存放庫名稱相同（轉成小寫 kebab-case）。

```md
---
title: <repo-name>
description: <一句話說明這個作品是什麼>
kind: repo
---

- 存放庫：<GitHub 網址>
- 分析日期：2026-01-31
- 分析時的 commit：<SHA 前 7 碼>

## 技術棧

語言、框架、主要套件與版本、建置與部署方式。

## 觀察

寫法、結構、測試、設定上值得注意的地方，好的與可改進的都寫。

## 引出的知識條目

- [<條目標題>](../../<concept>/<topic>/)：<為什麼這個作品引出它>
```

### 目錄索引

檔案位置 `src/content/docs/<concept>/index.md`。`sidebar` 那三行讓它在側邊欄顯示為「總覽」並排在最前面。

```md
---
title: <目錄的中文名稱>
description: <一句話說明這個目錄收什麼>
kind: index
sidebar:
  label: 總覽
  order: 0
---

<一兩句話說明這個目錄的範圍，以及什麼不放這裡。>

| 條目 | 摘要 | 狀態 | 優先度 |
|---|---|---|---|
| [<條目標題>](<topic>/) | <與條目 description 相同> | 待學習 | 高 |
```

## 索引列的格式

索引必須與實際檔案一致。新增、改名、移動、刪除條目時，在同一次變更內更新對應的索引。建置不會檢查索引有沒有漏列，變更後要自己列出目錄內的檔案，與索引逐列核對。

- **根索引**的「技術概念目錄」表格，每個目錄一列：

  ```md
  | [<目錄的中文名稱>](<concept>/) | <與目錄索引的 description 相同> | <條目數> |
  ```

  表格有了第一列之後，把下方「目前還沒有技術概念目錄」那句刪掉。

- **目錄索引**每個條目一列，格式見上方範本。狀態寫中文：待學習、學習中、已掌握。優先度寫中文：高、中、低。列的順序依優先度由高到低，同級依標題排序。

- **作品索引** `repos/index.md` 每個存放庫一列：

  ```md
  | [<repo-name>](<repo-name>/) | <技術棧摘要> | 2026-01-31 |
  ```

  表格有了第一列之後，把下方「目前尚未分析任何存放庫」那句刪掉。

條目的 `status` 或 `priority` 變動時，目錄索引那一列要跟著改。目錄的條目數變動時，根索引要跟著改。

## 連結寫法

站內連結一律用**相對網址**，以 `/` 結尾，不帶 `.md`。不要寫 `/` 開頭的絕對路徑，網站部署後網址有路徑前綴，絕對路徑會失效。

每個頁面的網址都是一個以 `/` 結尾的資料夾，所以從條目出發要多退一層：

| 從哪裡 | 連到哪裡 | 寫法 |
|---|---|---|
| 條目 | 同目錄的另一個條目 | `../<topic>/` |
| 條目 | 另一個目錄的條目 | `../../<concept>/<topic>/` |
| 條目 | 自己目錄的索引 | `../` |
| 條目 | 作品分析頁 | `../../repos/<repo-name>/` |
| 作品分析頁 | 條目 | `../../<concept>/<topic>/` |
| 目錄索引 | 自己目錄的條目 | `<topic>/` |
| 根索引 | 目錄索引 | `<concept>/` |

錯誤的寫法：`./<topic>.md`、`<topic>.md`、`../<topic>`（少了結尾的 `/`）、`/<concept>/<topic>/`。

建置時會檢查所有相對連結，指向不存在的頁面就會失敗。

一個概念只在一處完整說明，其他地方用連結帶過去，不要重複寫。

## 命名與文字

- 目錄與檔名用英文小寫 kebab-case，例如 `state-management/server-state.md`。檔名就是網址，定了之後盡量不改。
- 內容用繁體中文，技術名詞保留英文原文。
- 建議要具體到作品與檔案，避免「可以多了解 X」這類空泛的說法。
- 引用程式碼只取足以說明的片段，並標明檔案路徑。

## 內容的依據

- **主流要查證**：「目前主流」會隨時間改變，不要只靠記憶。寫入前用網路搜尋確認現況，以官方文件與版本發布紀錄為準，並把來源放進「參考資源」。查不到依據的說法不要寫成定論。
- **現況要有出處**：「我的現況」寫的每件事都要對得上存放庫裡實際的檔案，不要推測。
- **隱私**：不寫入金鑰、token、個人資料，也不抄錄私有存放庫的原始碼。要分析私有存放庫前，先問使用者它的名稱與分析結果能不能出現在公開網站上。

## 新增條目的流程

**先給大綱，使用者同意後才能寫入檔案。** 這一條沒有例外。

1. 沿索引確認是否已有相同或相近的條目。有的話改走「修改」，不要另建一篇。
2. 在對話中提出大綱，格式如下。
3. 等使用者明確同意。使用者要求調整，就改大綱再確認一次。
4. 寫入條目。
5. 在同一次變更內更新：目錄索引、對應的作品分析頁的「引出的知識條目」、條目數變動時的根索引。
6. 執行 `npm run build`，通過後再逐列核對索引。

大綱格式：

```md
**位置**：<concept>/<topic>.md（目錄：<目錄的中文名稱>）
**標題**：<title>
**摘要**：<description>
**狀態／優先度**：todo／<priority>，理由：<一句話>
**來源**：<repo-name> 的 <檔案路徑>
**標籤**：<tags>

**各段要點**
- 這是什麼：<一到三行>
- 我的現況：<一到三行>
- 與主流的落差：<一到三行，註明查證來源>
- 學習路線：<步驟標題>
- 動手練習：<一到三行>
- 參考資源：<預計引用的來源>

**連帶更動**：<會改到的索引與其他頁面>
```

一次分析常會產生很多候選條目。先給一份候選清單，每項一行（標題、所屬目錄、優先度、一句理由），讓使用者挑選，再對選中的逐一給大綱。不要一次送出一大批完整大綱。

## 新增技術概念目錄

新目錄也是新增內容，要放進大綱一起給使用者看，並說明為什麼現有目錄放不下。同意後：

1. 建立 `src/content/docs/<concept>/index.md`，用上方的目錄索引範本。
2. 在根索引的「技術概念目錄」表格加一列。
3. 在 `astro.config.mjs` 的 `sidebar` 加一組，照檔案裡的註解複製「作品分析」那一行，改 `label` 與 `directory`。少了這一步，目錄不會出現在網頁的側邊欄。

## 新增作品分析頁

分析一個新的存放庫時，建立 `repos/<repo-name>.md` 並在 `repos/index.md` 加一列。這一頁記錄的是事實（技術棧、檔案裡看到的寫法），可以直接建立，不需要先給大綱；由它引出的知識條目則照上面的流程走。

重新分析已有紀錄的存放庫時，先比對頁面上記錄的 commit 與目前的差異，只看有變動的部分，並更新分析日期與 commit。

## 修改既有內容

| 變更種類 | 做法 |
|---|---|
| 錯字、斷掉的連結、格式 | 直接改 |
| 使用者回報學習進度 | 直接改 `status`，並同步目錄索引 |
| 增刪段落、改結論、改 `priority`、改標題或摘要 | 先列出變更要點給使用者看，同意後才改 |
| 改檔名、搬到別的目錄、刪除條目 | 先問使用者，同意後連同所有指向它的連結與索引一起改 |

實質內容有變動時，把 `updated` 改成當天日期。只改錯字或格式不用動。

## 完成前的檢查

- [ ] 新增的內容都經過使用者同意
- [ ] frontmatter 欄位齊全，`description` 與索引列的摘要相同
- [ ] 目錄索引、根索引、作品分析頁都已同步
- [ ] 新目錄已加進 `astro.config.mjs` 的側邊欄
- [ ] `npm run build` 通過
- [ ] 列出目錄內的檔案，與索引逐列核對過
